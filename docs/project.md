## What the work needs

What every feature, and every AI factory run, starts from. **Required** means the work cannot
start without it; **optional** inputs make sure nothing is missed, but never decide — the FSD
does, and where it is silent the gap becomes a question in
[`open-questions.md`](open-questions.md).

| Input | Needed | Where it lives |
|---|---|---|
| The FSD | Required | `requirements/fsd/` — one file per revision, `<Name> - V<n>.<ext>`; build from the highest `V<n>` ([`read-me.txt`](../requirements/fsd/read-me.txt)) |
| A repository with a build and a test command | Required | No remote yet — `git remote add origin <url>` (https or ssh, never with credentials). Build `python3 -m compileall -q src tests`; tests `python3 -m pytest -q -p no:cacheprovider` ([commands] and [adapter] in `devtools/factory/factory.toml`) |
| People at the gates, and someone to answer the client's questions | Required | Each feature's owner (the **Owner** column below) approves; a teammate reviews; questions go through [`open-questions.md`](open-questions.md) |
| Designs, test cases, a release plan | Optional | Under `requirements/`, each listed in [`read-me.txt`](../requirements/read-me.txt); a release plan feeds only the delivery schedule |

# Part 1 — Features and phasing

Every feature is built from a plan in [`plans/`](plans/). This part is the index: what
exists, what it depends on, and where it has got to. **The detail is the plan's.**

## How plans work

1. **A feature gets a plan before it gets code.** Copy
   [`plans/_template.md`](plans/_template.md), name it after the feature, and link it from
   the feature's row below.
2. **The plan holds the feature's tasks**, in build order, each with its role and status.
   [Task progress](#task-progress) below is generated from them.
3. **The plan and the code stay in sync.** A departure from the plan updates the plan in the
   same commit.
4. **Questions the requirements cannot answer** go to
   [`open-questions.md`](open-questions.md), never into a plan as a guess.
5. **A plan is done when its feature is merged and its status here says so.**

**Status:** `Not started` · `In progress` · `Built` · `Blocked — <reason>`. An empty
**Plan** cell means the plan has not been written yet; plans are written on demand.
**Owner** is `—` until a person names one.

Every row cites the FSD section it comes from as `§<id> <title>`, exactly as the FSD numbers
and titles it, and every FSD section is either a feature's or listed under
[Sections that are not features](#sections-that-are-not-features).

# Part 3 — Requirements history

What changed between requirements revisions. **Every revision lives in
`requirements/fsd/`, one file per version ([`read-me.txt`](../requirements/fsd/read-me.txt)).
Build from the highest.**

**Diff each new revision before building from it and add a section here.** A revision
can silently answer an open question, or change a rule a built feature relies on;
without the diff we build from a stale assumption while believing the plan is current.
`/requirements-check` captures a new revision and records the comparison. When a new
revision arrives, its comparison goes here and the one it replaces moves to
[`archive/requirements-history.md`](archive/requirements-history.md), in this shape:
`## V<n-1> → V<n> · received <date>`, then *New requirements*, *Corrections to wrong
text*, *Renames and rewording*, *What did not change*, *What this lands on*, and *How this
comparison was produced*.
