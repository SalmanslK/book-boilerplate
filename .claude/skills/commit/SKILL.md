---
name: commit
description: >
  Smart commit: runs review-branch automatically, then stages and commits with a
  short human-style imperative message if the review passes. Never commits to a
  protected branch. No AI or tooling attribution, no trailer lines.
---

Follow these steps exactly.

## Step 0 — Check the branch

Run `git branch --show-current` and compare it with `protected_branches` in
`devtools/factory/factory.toml` (and any the project's `CLAUDE.md` names).

- **On a protected branch: STOP. Do not commit.** Protected branches are
  reached by pull request only. Tell the user, and suggest
  `git checkout -b <type>/<slug>` — it keeps the uncommitted changes and moves
  them onto a new branch. Do not create the branch yourself unless asked.
- **Detached HEAD, or in the middle of a merge or rebase: STOP** and say so.

The guard refuses a commit on a protected branch too; this step exists so the
review is not wasted first.

## Step 1 — Code Review

Invoke the `review-branch` skill and wait for the full output.

- If the verdict is **"NOT READY – Fix blockers before submitting PR"**:
  - Show the blockers to the user
  - STOP. Do not commit.

- If the verdict is **"READY – Safe to submit PR"**: continue to Step 2.

The review covers the whole branch, including what is about to be committed.
Run it once per invocation of this skill, not once per commit group.

## Step 2 — Assess commit grouping

Run `git status` and `git diff --stat` to see all changed and untracked files.

**Leave out anything that does not belong to this change** — editor and tool
droppings, local scratch files, generated output the project does not track.
If you are unsure whether a file belongs, ask rather than stage it.
**Never stage a file that looks like it holds a secret** (an `.env`, a key, a
settings file with real values); say so and leave it out.

**Single logical concern** (one tightly coupled fix or feature): proceed to
Step 3 for a single commit.

**Multiple logical concerns** (e.g. application fix + new tooling + docs):
split into multiple commits, each independently meaningful. Do NOT pile
unrelated changes into one commit.

Grouping strategy — commit in this order:
1. **Application code** (the project's source folders) grouped by the fix or
   feature they belong to
2. **Tests** that cover the application changes above
3. **Tooling / skills** (`.claude/`, `devtools/`, config files)
4. **Documentation** (`CLAUDE.md`, `docs/`, README)

**Except where the project requires them together.** A rule like "change
behaviour, fix the doc that owns it in the same commit" or "the plan and the
code stay in sync, in the same commit" wins over this ordering: the doc or
plan goes in the same commit as the code it describes. So does a regenerated
file with the change that regenerated it.

For each group:
- `git add` only the files for that group, by explicit path — never
  `git add -A` or `git add .`
- Generate a short imperative commit message for that group (same rules as
  Step 3)
- `git commit -m "<message>"` — Step 1's review already covered the whole
  branch; do not re-run it per group

## Step 3 — Generate commit message

Run `git diff --cached --stat` to understand what is staged.

Write a commit message that:
- Is a single short line (under 72 characters)
- Uses imperative mood ("add", "fix", "update", "remove")
- Describes WHAT changed, not HOW
- Sounds like a normal developer wrote it — no AI phrasing
- Carries the defect or question id when the change fixes a logged one
  (e.g. `D4`), and a ticket key if the project's `CLAUDE.md` asks for one
- Has NO body, NO description, NO co-author lines, NO "Generated by" text

Examples:
```
add user preference endpoint with migration
fix timezone default in user preference
rename preferences table to user_preferences
fix duplicate order on retried checkout (D4)
```

## Step 4 — Commit

Run:
```
git commit -m "<your generated message>"
```

Do NOT use a heredoc. Do NOT add `Co-Authored-By` or any trailer lines.
Do NOT mention Claude, Anthropic, or AI tooling anywhere in the commit.

**Never bypass a hook** — no `--no-verify`, no disabling signing. If a
pre-commit hook fails, show its output, stop, and leave the fix to the user
or to a new round of this skill. A failed hook means the commit did not
happen: do not `--amend` afterwards as if it had.

**Never push.** Committing is this skill's last step.

## Step 5 — Report

Run `git log --oneline -<n>` for the commits just made and show them, with
what was deliberately left unstaged and why.
